# docs/

Документация проекта. Этот файл — соглашение о том, **куда что складывать**. Если сомневаешься, где должен жить документ, найди ответ здесь, а не создавай новую папку.

## Главный принцип

Всё делится по **режиму поддержки**, а не по теме:

- **Живые документы** (`refs/`) — держим в актуальном состоянии. Изменилось — правим файл.
- **Записи на момент времени** (`adr/`, `meets/`, `notes/`) — не редактируем после написания. Устаревшая запись здесь не ошибка, а исторический факт.

Смешивать режимы нельзя: если в папку, где записи только добавляются, попадёт документ, который надо поддерживать, ей перестанут доверять как журналу.

## Куда складывать — быстрый ответ

| Вопрос про документ | Папка |
|---|---|
| Это выбор между альтернативами, который кто-то захочет оспорить позже? | `adr/` |
| Это произошло на встрече или в переписке? | `meets/` |
| Я просто хочу не наступить на эти грабли снова? | `notes/` |
| Это описание **чужой** системы (API, поставщик, зависимость)? | `refs/external/` |
| Это описание того, как устроена **наша** система сейчас? | `refs/internal/` |
| Это план реализации задачи? | → рабочий план задачи вне `docs/` (формат зависит от используемого фреймворка) |
| Это договор / NDA / SOW? | → вне Git (Drive/Notion), в репозитории только ссылка |

## adr/ — решения

**Режим:** неизменяемый. Принятый ADR не редактируется — его вытесняет новый (`superseded`), а не правка.

Зафиксированные архитектурные и технические решения в формате: контекст → решение → рассмотренные альтернативы → почему выбрано → последствия.

- **Тест:** «это выбор между вариантами, который через полгода захотят оспорить?»
- **Пример:** «Выбрали БД X вместо Y, потому что нужна гео-репликация; последствия — зависимость от облака поставщика.»
- **Не сюда:** подробное описание текущей схемы модулей (→ `refs/internal/`); факт, что решение приняли на встрече (→ `meets/`).
- **Источник:** сюда **переносятся вручную** значимые решения из рабочих планов задач. Не копируй автоматически сгенерированные ADR пачкой — только то, что устоялось.

## meets/ — записи встреч

**Режим:** новые записи добавляются по датам, старые не редактируются.

Короткие встречи, протоколы, договорённости — и с командой, и с клиентом. Фиксирует, кто что сказал и о чём договорились на конкретный момент. Сюда же асинхронные договорённости из переписки.

- **Формат имени:** `2026-06-16-sync.md`, `2026-06-20-client-scope.md`.
- **Тест:** «это произошло на конкретной встрече или в переписке?»
- **Не сюда:** строгая формулировка принятого решения (→ `adr/`). `meets/` фиксирует *факт*, что решение принято, и **ссылается** на ADR, а не дублирует его тело.

## notes/ — наблюдения и грабли

**Режим:** новые записи добавляются без правки старых. Устаревшая запись не проблема — она была верна на свой момент.

Подводные камни, «почему здесь костыль», поведение, которого нет в чужой документации. Лабораторный журнал реализации.

- **Тест:** «я хочу не наступить на это снова?»
- **Пример:** «Поставщик дублирует вебхуки ~1% времени — отсекаем дубли по `event.id`. У них ошибка, заявка #123.»
- **Не сюда:** то, что надо поддерживать в актуальном виде (→ `refs/`); наблюдение, дозревшее до решения «поэтому переходим на Y» (→ рождается `adr/`).
- **Привязка:** заметка про **конкретную задачу** живёт рядом с рабочим планом задачи, в формате текущего фреймворка. В `docs/notes/` — только **сквозное**: про подсистему, поставщика, грабли, всплывающие в разных местах.

## refs/external/ — внешний мир

**Режим:** живой документ. Меняется внешний API — правим файл.

Описания внешних API, контракты интеграций, особенности зависимостей и поставщиков. То, к чему обращаешься, чтобы понять контракт того, что **не мы писали**.

- **Тест:** «это про чужую систему, и мне нужен её контракт?»
- **Пример:** «Точка API для оплаты у поставщика X: `POST /charges`, авторизация Bearer-ключом, подпись вебхука в заголовке `Y`.»
- **Граница с `notes/`:** `external` описывает контракт, **как он описан и задуман**; `notes/` ловит **отклонения, выясненные на болезненном опыте**. «Подпись в заголовке Y» → `external`. «Дублирует вебхуки 1% времени» → `notes`.

## refs/internal/ — наша система

**Режим:** живой документ. Внутренний близнец `external`: тот же режим (правим при изменениях), другой субъект.

Как устроена **наша** система сейчас: схема сервисов, как связаны модули, потоки данных.

- **Тест:** «это про текущее устройство нашей системы?»
- **Не сюда:** обоснование «почему выбрали так» (→ `adr/`). Если в `internal` появляется «потому что выбрали X вместо Y» — кусок просится в `adr/`.
- **Старт:** пока объём маленький — живёт в корневом `README.md` проекта и в коде. Заводи отдельные файлы здесь, когда раздел архитектуры перестаёт влезать на экран или появляется 2-3 подсистемы со своими страницами.

## Что НЕ живёт в docs/

- **Планы реализации** → рабочие планы задач вне `docs/` (формат и путь зависят от используемого фреймворка). `docs/` — курируемый слой; планы — рабочий процесс агента или команды. Значимые решения из планов переносятся в `adr/`.
- **Состояние, черновики и служебные артефакты агента/фреймворка** → в `.gitignore` или рабочую директорию фреймворка, не в `docs/`.
- **Юридические документы клиента** (договоры, NDA, SOW) → вне Git, в защищённом хранилище (Drive/Notion). В репозитории максимум ссылка. Секреты и доступы в репозитории не храним никогда.

## Разрешение спорных случаев

- **Решение, принятое на встрече:** факт «решили на встрече» → `meets/`; формулировка решения → `adr/` со ссылкой из `meets/`. Тело решения — в одном месте.
- **Наблюдение, дозревшее до решения:** пока «заметил, что X тормозит» → `notes/`; когда «поэтому переходим на Y» → `adr/`.
- **«Как устроено» и «почему так»:** устройство (поддерживаемое) → `refs/internal/`; обоснование (неизменяемое) → `adr/`.
- **Чужой контракт и наши грабли:** задокументированный контракт → `refs/external/`; выясненное отклонение → `notes/`.
